# 0.0.8 process CPU and memory validation — 2026-10-16

This records process measurements for the independent [preview PR #75](https://github.com/chriscco/slime/pull/75)
and [settings/updater PR #76](https://github.com/chriscco/slime/pull/76). It is not a release
acceptance result or a comparison against an older version.

## Environment and units

- Hardware: Apple M4, Mac16,12, 16 GiB RAM.
- Host: macOS 27.0, build 26A428. The supported minimum macOS 26 was not exercised here.
- Release builds; no concurrent builds, unit tests, or CPU benchmarks during samples.
- `proc_pid_rusage(pid, RUSAGE_INFO_V2)` sampled every 250 ms. Footprint means
  `ri_phys_footprint` in MiB, not resident memory, virtual address space, or app bundle size.
- CPU is process user + system CPU time divided by elapsed wall time; 100% represents
  one fully occupied core. A 250 ms peak is not an instantaneous peak.

The initial collector incorrectly treated Mach CPU ticks as nanoseconds. On this host,
`mach_timebase_info` returned numerator 125 / denominator 3. All CPU values below include
that conversion. Cross-check while the native harness was running: raw user + system
95,362,936 ticks × 125/3 / 1e9 = 3.973456 seconds, matching `ps` cumulative TIME 3.97 s.
The original CPU percentages were therefore low by a factor of 41.6667; memory values
were unaffected. Raw-derived first-run records were rescaled, and subsequent sampling
uses the corrected collector. Apple’s [XNU rusage implementation](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/bsd_kern.c)
assigns task CPU counters to these fields; the local timebase/`ps` cross-check is the
calibration evidence for this machine.

## Native preview workload

UI automation timed out, so active workload uses a separate release-built native API
harness. Its source is a temporary copy of the preview branch with only the entry point
and thumbnail-cache location changed. It calls the real `WindowEnumerator`, `AppIcons`,
`WindowThumbnails`, `PanelController`, search, and view/layout code. Screen Recording and
Accessibility preflight both return true; enumeration returns exactly 11 real windows.

The harness uses isolated UserDefaults and `/tmp` thumbnail files. It opens/dismisses only
its own nonactivating panel and never activates or closes a target window. Each cycle opens
the panel, waits 350 ms, performs five append/delete-query and selection pairs at 80 ms
intervals, dismisses, then waits 400 ms. It refreshes real enumeration on open. Per mode:
5 s warm-up, 15 s idle, approximately 20 s active, 3 s settle, 15 s recovery. Cached then
fresh run in the same process; framework and rendering caches are therefore warm for the
second mode. These are not independent cold-start memory comparisons.

First run (PID 31667) completed 12 cycles per mode. Corrected average active CPU was
9.888% cached / 10.128% fresh; peak footprint was 29.251 / 32.307 MiB. The second run (PID 32172) repeated
12 cycles per mode, with the panel visible in every cycle. End-of-cycle queries of
`WindowThumbnails.image(for:)` counted exactly 3/11 accepted previews in cached mode and
8/11 in fresh mode throughout; remaining cards used their fallback. These counts mean
images accepted by the renderer’s validation, not separate visual review of every image.

| Mode / phase | Seconds | Average CPU | Peak CPU (250 ms) | Footprint start → end | Peak footprint |
|---|---:|---:|---:|---:|---:|
| Cached / idle | 15.22 | 0.0007% | 0.02% | 15.548 → 15.360 MiB | 15.548 MiB |
| Cached / active | 20.05 | 8.9793% | 23.67% | 16.829 → 27.204 MiB | 30.876 MiB |
| Cached / recovery | 15.21 | 0.0147% | 0.28% | 26.970 → 26.266 MiB | 26.985 MiB |
| Fresh / idle | 15.22 | 0.0072% | 0.34% | 26.329 → 26.313 MiB | 26.407 MiB |
| Fresh / active | 20.07 | 10.5907% | 20.72% | 29.016 → 26.532 MiB | 35.032 MiB |
| Fresh / recovery | 15.24 | 0.0253% | 0.49% | 26.188 → 25.860 MiB | 26.188 MiB |

In this bounded workload fresh mode displayed more accepted images and used approximately
1.61 percentage points more average process CPU during activity. Both modes returned below
0.03% average process CPU during recovery. Retained footprint settled around 26 MiB after
both active phases; this is a short observation, not a leak test or a universal cost bound.

## Limits and remaining acceptance

- Process CPU excludes WindowServer, GPU, and other capture-service work. This is not
  a total-system energy measurement, a battery-life prediction, or an improvement claim.
- API-driven panel activity bypasses the event tap and physical keyboard delivery. It does
  not measure input-to-display latency; the existing 300 ms presentation cap remains code
  behavior, not proof of perceived smoothness on every machine.
- Eleven cards do not imply eleven usable screenshots. Blank/unavailable captures retain
  the icon fallback; the instrumented run reports image counts explicitly.
- A short recovery window can show quiescence and retained footprint, but cannot prove
  absence of slow leaks or establish a worst-case memory bound.
- Exact Stage Manager/minimized/other-Space classification, multiple displays, and native
  macOS 26 acceptance remain open. Useful perspective output was inspected on macOS 27.0;
  neither that evidence nor these CPU figures completes the shared spec’s native matrix.

Raw collector JSON, the temporary native harness, and logs are retained locally in `/tmp`;
no private window titles or screenshots are included in this record.

## Stage Manager follow-up for the README

The owner confirmed that Stage Manager was enabled with windows set aside in its left
strip. The harness independently checked `com.apple.WindowManager/GloballyEnabled`
before and after the run and reported two connected displays. It did not activate,
rearrange, minimize, or close target windows. This is a mixed desktop/Stage Manager
workload, not a panel containing only individually classified side-strip windows.

The `cached` preference reuses earlier memory/disk previews; `fresh` bypasses stored
previews and captures anew on panel opening. Both retain images within the current
session, so filtering does not request another capture. The preference applies to the
whole panel, not just Stage Manager windows. Product thumbnail code matches `05a8cfc`,
except that the harness writes only to its isolated temporary thumbnail directory.

A preliminary follow-up kept 10 windows through both active phases. It completed
13 show/search/dismiss attempts per mode, but observed only 12 visible panels in cached
mode versus 13 in fresh mode. Average CPU was 8.473% / 7.978%, and peak footprint was
33.673 / 35.610 MiB (cached / fresh). These observations are retained here but not used
for the README comparison: first presentation and effective operation counts differed.
The reason for the single hidden-panel observation was not isolated.

The README run therefore prewarms panel presentation for each mode before idle sampling,
uses exactly 12 cycles, checks that the panel is visible on all 12, and records minimum
and maximum window counts. It waits 250 ms after starting each active sampler, runs
those cycles within the 20-second phase, then waits out any remainder. Each mode uses
the same input sequence and timing. Cached runs before fresh in the same process, so
these remain warm-process observations, not randomized independent cold starts.

The fixed-cycle run observed 11 windows throughout both modes (the owner’s window set
changed between the preliminary and fixed-cycle runs). Screen Recording and Accessibility
were available; every measured cycle observed a visible panel. Both mode warm-ups also
confirmed visible panels. Accepted image counts stayed at 3/11 cached and 8/11 fresh.

| Mode | Active sample | Average CPU | Peak CPU (250 ms) | Peak footprint | Visible cycles |
|---|---:|---:|---:|---:|---:|
| Cached | 20.05 s | 9.8895% | 18.86% | 28.970 MiB | 12 / 12 |
| Fresh | 20.04 s | 10.0902% | 18.47% | 34.626 MiB | 12 / 12 |

README values are rounded to one decimal place. The small CPU difference is not evidence
that either mode is consistently faster: capture availability, warm-cache order, and
short sampling windows affect the result. Unavailable previews still use fallback cards;
11 windows does not mean 11 full-size screenshots. No private titles or images are published.

Stage Manager remained enabled at exit. Recovery averaged 0.0124% CPU / 26.235 MiB
ending footprint in cached mode and 0.0142% / 25.688 MiB in fresh mode. Both mode
sampling intervals completed, all visibility assertions passed, and the harness exited 0.
Local follow-up logs: `/tmp/slime-stage-manager-fixed-results.log`; raw summaries use
`/tmp/slime-perf-stage-manager-fixed-{cached,fresh}-{idle,active,recovery}.json`.
