# Settings and updates implementation plan

Goal: native settings closure, rounded local About artwork, and signed in-app updates.
Architecture: one AppKit-owned Sparkle controller exposes check/preference state to
settings; standard Sparkle UI owns download/installation/restart. Reuse tagged release
DMGs and add a signed appcast without exposing credentials.
Constraints: macOS 26; user confirmation before install; automatic checks opt-in;
self-signed distribution until separately changed; no analytics; no publication or
production key creation without explicit setup; no replacement custom installer.

- [x] Verify stable Sparkle release APIs, SwiftPM integration, nested code signing, and
  appcast generation with official docs/source. Pin exact version and lock resolution.
- [x] Add a failing AppKit test sending Command-W to the settings window and verifying
  close plus other-window isolation. Add a settings-window key equivalent and retest.
- [x] Update About tests to verify a bundled 3:1 image, clipping/radius, accessible label,
  version and repository controls. Copy the shared banner during bundle construction;
  verify the image container fits the scrollable content area in layout tests.
- [x] Render and inspect About in light/dark with the actual controller and packaged banner;
  native packaged-window interaction remains a separate acceptance gate.
- [x] Test updater controls using isolated bundle preferences, then
  implement SPUUpdater with SPUStandardUserDriver integration, launch initialization, check action,
  opt-in auto-checking, and no automatic installation. Disabled development configuration
  must show a clear state instead of contacting an invalid feed.
- [x] Test release metadata validation (missing keys, invalid artifact signature, version
  mismatch, metadata URLs) with Python stdlib. Extend packaging to embed/sign Sparkle,
  set public key/feed metadata, and verify nested bundle/framework/helper loadability.
- [x] Extend release workflow to sign existing DMG and generate appcast before publication;
  upload with checksum/notes in the existing release transaction. Document exact new secret
  and public key setup, preserving current signing identity and failure recovery.
- [x] Use disposable update keys and isolated app copies to exercise real signed updater
  validation. Never install a test update over the user's actual slime. Record limitations
  when GUI approval or production key setup requires the owner.
- [ ] Run scripts/test and release script tests, build release app/DMG, check CI, self-review,
  update module docs + 0.0.8 notes, open PR closing #73. Leave merge/publication to owner.
