# 0.0.8 settings and updates validation

Recorded 2026-10-16 for issue #73 on `feat/settings-updates`. This records implementation
checks, not release approval. Version 0.0.8 is unreleased; production update keys and the
first appcast have not been configured or published by this work. Local native checks
ran on arm64 macOS 27.0 (26A428); the macOS 26 deployment baseline remains a separate gate.

## Automated and packaging checks

- `scripts/test`: 186 tests passed, including the settings window-level regression. Tests cover local Command-W closure, constrained 3:1 banner layout/accessibility,
  invalid updater configuration, explicit automatic-check preference persistence, and
  controls updating without replacing the focused view.
- `python3 -m unittest discover -s scripts/tests`: 18 tests passed. Coverage includes missing
  keys, release metadata mismatch, HTTPS artifact URL/size/arm64 requirements, private-key
  stdin transport without inherited child environment, and sanitized tool failures.
- Actual pinned Sparkle signing tools signed/verified ephemeral fixtures and rejected a
  different private key, a modified archive, and modified signed XML content. Disposable
  CryptoKit seeds remained in memory/stdin; no production key or Keychain item was created.
- Release app/DMG built with the existing selfsigned identity. Deep/strict verification
  passed for app and embedded helpers; mounted DMG inspection matched executable, plist,
  icon, and banner. Framework symlinks/modes and executable Frameworks runpath were checked.
  Packaging also copies the pinned distribution license into Resources and verifies the
  same license in the mounted DMG; a build-script regression checks that it is retained.
- `scripts/sign-updates v0.0.8` generated and verified a real signed appcast and DMG with
  disposable keys, embedded notes, minimum macOS 26.0, arm64 requirement, and an immutable

- HTTPS-only requests to GitHub's existing latest DMG followed its immutable tagged URL
  and the HTTPS asset host to HTTP 200. The proposed latest appcast returned HTTP 404 as

  exercised against production Releases.

## Isolated install and relaunch

build-1/build-2 copies, the existing signing identity, and ephemeral Ed25519 keys. Official
Sparkle tools signed a build-2 zip and appcast. A loopback-only server served them; only the
test bundles allowed local HTTP. Production configuration still requires HTTPS.

A custom `SPUUserDriver` supplied the two positive decisions: download, then install/relaunch.
Sparkle's real engine verified, downloaded, extracted, replaced the isolated old app, and
relaunched build 2. The relaunched executable wrote `relaunch-success`; the original app
path contained build 2 and passed `codesign --verify --deep --strict`.

Observed stages: `launched-version-1`, `checking`, `confirmed-download`, `downloading`,
`extracting-verified-download`, `confirmed-install-and-relaunch`, `installing`,
`launched-version-2`. Both feed/archive HTTP requests returned 200. A nonfatal sandbox
extension warning appeared on stderr, but replacement, relaunch, and final signing passed.
The loopback server stopped, test processes exited, and UUID defaults/cache were removed.
No production slime bundle, preferences, or permissions were changed.

The same success case was repeated with a signed **DMG** update containing the app and
Applications symlink, matching the production archive format. `python3 /tmp/slime-updater-smoke.py dmg` fetched appcast.xml/update.dmg, replaced build 1 with 2,
relaunched with the success receipt, and passed final strict signature verification.
Its public fixture directory ends in `slime-install-smoke-wn_5fz_l` under the same temporary
root. Both zip and DMG installation paths passed; no production app was replaced.

Local evidence (temporary, not required to read this record):

## Isolated runtime failure cases

The same local harness accepts a scenario argument. Each invocation builds fresh UUID
host copies and disposable keys; all cases below preserved build 1, passed strict signing
verification on that original app, and produced no update relaunch receipt.

| Command argument | Observed runtime outcome |
|---|---|
| `cancel` | Dismissed the update offer before download; no archive request. |
| `equal` | Build 1 feed returned Sparkle 1001, no-update reason 1 (up to date). |
| `downgrade` | Build 0 feed returned Sparkle 1001, no-update reason 2; no downgrade. |
| `offline` | Stopped loopback server returned Sparkle 2001 with URL error -1004. |
| `unsupported` | Minimum macOS 99.0 returned Sparkle 1001, no-update reason 3. |
| `corrupt` | Modified downloaded bytes were rejected before unarchiving, errors 4005/3002. |
| `badsig` | Correct-length archive with a bad EdDSA signature in a re-signed feed was rejected before unarchiving, errors 4005/3002. |
| `readonly` | Host launched from a read-only mounted DMG returned Sparkle 1003 and requested copying to Applications. |

Example: `python3 /tmp/slime-updater-smoke.py readonly`. The read-only image was detached;
servers, host processes, unique preferences, and caches were cleaned up after each run.
The custom driver's extraction callback log is a progress notification, not proof of
successful verification; the invalid-signature cases explicitly failed before unarchiving.

## Native acceptance still required

  The harmless test host intentionally never requests those permissions.
- Final native packaged-window interaction and screenshot. Light/dark offscreen renders
  using the actual settings controller and packaged banner were visually inspected after
  correcting the test compositor: contrast, rounded artwork, and layout fit at 720 pt.
  The render host shows its development version by design; native UI automation did not

Keep these as release gates. Successful signing and isolated installation do not certify
those behaviors or add Developer ID signing/notarization. The first updater-enabled release
requires manual installation because 0.0.7 has no updater.

above. Independent code review identified floating settings obscuring ordinary updater
