# slime 0.0.7 — Panel themes and search header

- **Status:** Implemented; native user acceptance pending.
- **Issue:** #61
- **Delivery:** Spec and implementation share `feat/0.0.7` and one final PR. No spec-only merge.

## Goal

Make panel appearance selectable and understandable through visual previews, and give
search a recognizable slime identity with a visible focus shortcut.

## Confirmed direction

The maintainer approved four background choices, miniature panel previews, a square
slime logo outside the search field on its left, and the lightweight toolbar design.
The Command-F keycap appears when search is unfocused, hides on focus, and returns
when focus ends. Direct typing continues to filter windows.

This spec makes remaining layout and compatibility choices concrete for review.

## Scope and constraints

- macOS 26+, Swift 6, AppKit, zero third-party dependencies.
- Preserve five-column layout, grouping, scrolling, selection, and window identity.
- Preserve Command-Tab release-to-switch, Option-Tab persistence, direct typing,
  Command-F focus, and the existing close transaction and CRT animation.
- Preserve user-selected accent color, glass style, glass strength, and panel corners.
- English and Simplified Chinese settings labels remain available.
- The final implementation updates bundle version to 0.0.7 / build 7 and relevant
  README and module documentation. Tagging, DMG publication, and release replacement
  are separate work; this task does not publish a release.

## Non-goals

- Arbitrary background color picking: this version deliberately offers four choices.
  Revisit only if users need colors outside the presets.
- New search editing semantics, IME composition, or caret travel animation: this work
  changes presentation, not the tap-owned query model.
- Animated logos, continuous preview rendering, or live window capture in settings:
  static illustrations are sufficient to compare themes without background work.
- A wholesale settings redesign or per-window theme controls: use the existing
  Appearance section and panel-wide preferences.

## 1. Background selection

Add one persisted `Settings.PanelBackground` choice with stable raw values:

| Value | English / Chinese label | Base color | Panel appearance |
|---|---|---|---|
| `black` | Black / 黑色 | sRGB #000000 | Dark Aqua |
| `white` | White / 白色 | sRGB #FFFFFF | Aqua |
| `deepBlue` | Deep Blue / 深蓝 | sRGB #0A2C37 (10, 44, 55) | Dark Aqua |
| `system` | System / 跟随系统 | Black in dark mode, white in light mode | Resolved from system appearance |

Use black when the preference is absent or unrecognized. Existing installations and
fresh installs therefore retain the current default. Do not reset accent or other
appearance preferences when introducing this key or changing the selection.

Fixed choices ignore system light/dark changes. System follows the application's
system-derived appearance, not an appearance already forced on the panel. Resolve it
on presentation and respond to appearance changes while the panel is visible. A
hidden panel must use the current system appearance when next shown.

Apply the resolved appearance and base color together. Refresh appearance-dependent
layer colors as well as dynamic text colors: cached CGColors do not update themselves.
This includes search, shortcut keycap, empty state, group labels, card titles, and
fallback preview decoration. Actual window thumbnail images remain unchanged.

### Glass interaction

Keep the existing compositing model: a base-color mask over the glass with
`alpha = 1 - glassStrength`. Strength 0 is opaque; strength 1 has no base-color mask,
so preset colors may become indistinguishable at that endpoint. Appearance still
controls foreground styling. Do not silently change strength to make a preset visible.

The deep-blue RGB value describes the base color, not a promise that every composited
screen pixel equals that value. Desktop content and glass style affect the result.
Settings includes a short localized explanation of this relationship.

## 2. Theme previews in settings

Add four equal-sized selectable miniature panel cards to the Appearance section,
above the existing glass controls. Each shows a stylized search header and window
cards, followed by its localized name. Use a two-column grid so labels and previews
fit the existing settings content width without shrinking text or widening the window.

- Black, White, and Deep Blue show their own base and matching foreground palette.
- System uses a split light/dark illustration so its meaning remains visible in
  either current system appearance.
- A checkmark and visible selection outline identify the persisted choice. Selection
  must not rely on color alone.
- Clicking anywhere on a card selects it. Keyboard focus plus Space activates it.
  Expose each choice's localized name and selected state to accessibility.
- Use static AppKit drawing/views with schematic content, not screenshots of users'
  windows. These previews depict the base theme at a fixed opaque strength; existing
  glass sliders do not cause preview capture or animation.
- Label the previews as illustrative; the explanatory copy states that glass strength
  changes the actual appearance. Preview geometry need not reproduce the full panel.
- Selecting a card saves immediately through the existing settings change callback.
  Apply it to an already-visible panel, or on its next presentation if dismissed.
- Keep all appearance controls reachable at the existing window size; use existing
  scrolling/layout support or add content scrolling if the preview grid requires it.

## 3. Branded search toolbar

Use the existing header region and retain the grid's vertical origin and overall
panel sizing. The header's available control height is 32 pt in the current layout.

Layout, from left to right:

1. A 32 × 32 pt slime logo outside the input, vertically centered in the header.
2. A 10 pt gap.
3. A search field filling the remaining header width.

Use the existing square app artwork from the packaged resources; reuse the app icon
resource rather than introducing a second independently maintained logo. Preserve
its aspect ratio, do not tint or animate it, and avoid per-keystroke image loading.
The logo is decorative, has no click action, and does not enter keyboard focus order.
If the resource cannot be loaded in a test or command-line launch, retain geometry
without crashing or displaying another application's icon.

### Search styling and focus

- Use a 10 pt corner radius, 15 pt system text, and 12 pt horizontal content insets.
- Remove the old magnifying-glass icon; the separate slime logo anchors the header.
- Unfocused: a subdued neutral fill that is distinct from the selected panel base,
  no prominent outline, placeholder/query on the left, and a Command-F keycap on
  the right. Placeholder remains localized as “Type to filter” / “输入以过滤”.
- Focused: retain the clear 2 pt accent border and a subtle accent fill. Show the
  existing blinking end caret; hide the Command-F keycap.
- The keycap reads `⌘F`, uses a 12 pt medium system font, a small rounded background,
  and secondary text color. It is a passive hint, not a new button or shortcut handler.
- If focus ends without dismissing the panel, restore the keycap. A newly presented
  unfocused session also shows it, with no stale hidden state from the previous one.
- Existing close status messages take priority over the passive hint: temporarily
  hide the keycap while a status message is visible, restoring it when the message
  clears if search remains unfocused.
- Reserve trailing space for whichever item is visible. Query text and caret are
  clipped within the remaining area and cannot overlap the keycap or status message,
  including long queries and narrow-screen panel layouts.
- Keep the query, selected window, and focus state unchanged when the theme changes.

Use semantic text colors and appearance-aware neutral fills. Verify the default
slime-green focus border against white as well as dark backgrounds. If its contrast
is insufficient, add a subtle neutral edge beneath the accent border rather than
changing the user's saved accent. The visible focus state must remain distinguishable
with the default accent and with very light custom accents.

Keep caret positioning immediate and preserve existing Reduce Motion behavior.
No new repeating animation or implicit theme-transition animation is required.

## 4. Implementation boundaries

- `System/Settings.swift`: persist the background enum, fallback, and theme resolution
  alongside existing appearance settings. Use injected UserDefaults in tests.
- `UI/PanelWindow.swift`: apply base and resolved appearance; refresh layer palettes;
  own the logo, search keycap, and header geometry in existing PanelContentView.
- `UI/PanelController.swift`: integrate theme refresh with existing presentation and
  settings updates without rebuilding window enumeration or resetting the session.
- `UI/SettingsWindow.swift`: add selectable previews and localized explanation through
  existing settings callbacks. Use small drawing code instead of an image pipeline.
- `UI/CardGridView.swift`: update any fixed dark-only decoration that becomes incorrect
  under Aqua; retain original thumbnails and selection/closing behavior.
- `App/AppDelegate.swift`: change only if necessary to forward application appearance
  changes through the existing settings/panel update path.
- `scripts/build-app`: version 0.0.7 / build 7; ensure the reused icon is available.

Do not add a generalized theme engine or a new dependency. Keep system color handling
out of Core. Appearance updates occur on the main actor, outside the event-tap callback.

## 5. Performance and failure behavior

- No new AX queries, window enumeration, thumbnail requests, polling, or timer for themes.
- Resolve the theme on settings/system changes and panel presentation, not each frame.
- Reuse the loaded logo and preview views. Theme changes update colors and selection
  state; they do not recreate window capture resources or reload every thumbnail.
- Preserve the existing shared glass surface rather than giving each settings preview
  its own live glass compositor.
- Unknown saved theme values fall back to black without erasing other preferences.
- A theme update during a close animation must not cancel, restart, or retarget closing.
  The existing CRT snapshot can finish in its original palette; the remaining UI uses
  the new palette. The callback must not reopen a dismissed panel.

## 6. Acceptance and validation

### Automated behavior checks

- Fresh/unknown preferences resolve to black; all four values survive Settings
  reconstruction using the same injected defaults; other saved preferences survive.
- Fixed themes resolve identically under light/dark input. System resolves to black /
  Dark Aqua or white / Aqua respectively. Deep Blue resolves to sRGB (10, 44, 55).
- Applying a light/dark theme refreshes relevant layer colors without clearing query,
  selection, or search focus.
- Unfocused search shows `⌘F`; focus hides it; loss of focus restores it. Close status
  temporarily overrides it. Repeated presentations do not retain stale hint state.
- Logo, text clipping, caret, hint, and status frames stay within the header and do not
  overlap at normal and narrow supported widths, including long queries.
- Settings preview controls reflect the saved choice, persist activation, and expose
  accessible names/selection. Settings layout keeps the final control reachable.
- Existing trigger, layout, selection, and close tests pass unchanged unless an
  assertion intentionally describes the replaced header geometry.

Use `SettingsTests.swift`, `PanelLayoutTests.swift`, and `SettingsWindowTests.swift`
for these seams. Follow red → green behavior tests. Run `scripts/test`,
`scripts/build-app`, `git diff --check`, and the final head's CI `test` job.

### Packaged-app manual acceptance

1. Choose each theme, reopen the panel, restart slime, and confirm persistence and
   readable search, titles, empty state, group headers, and fallback thumbnails.
2. Select System; toggle system light/dark while visible and while hidden. Verify the
   panel updates or opens in the current appearance. Fixed themes must not switch.
3. Inspect all themes at glass strength 0, the default 0.2, and 1; confirm the documented
   endpoint behavior without silently changing the slider.
4. Confirm the square slime artwork is visible in the built app. Inspect settings
   previews and compare their base palettes with the opaque panel.
5. Open with Command-Tab: observe `⌘F`, press Command-F, observe its disappearance and
   the focus border/caret. Repeat with direct typing and Option-Tab. Check release,
   Escape, selection, and close behavior remain unchanged.
6. Inspect normal/narrow screen widths, long queries, close failure status, grouping,
   white-background focus contrast, and Reduce Motion. Verify no overlap or clipped
   controls; inspect light and dark settings appearances and keyboard activation.
7. With the panel idle, confirm theme previews introduce no recurring capture or
   animation work. Record any measured performance results separately; do not claim
   frame-rate or CPU improvements without measurements.

Record which checks actually ran. Automated checks do not substitute for native glass
and visual acceptance; any unavailable manual checks must be listed in the PR.

## Design alternatives and tradeoffs

- Miniature schematic previews over screenshot assets: no private window content,
  localization drift, or extra capture work; glass appearance remains illustrative.
- Lightweight rounded toolbar over a pill or borderless search area: maintains a
  recognizable input and visible focus while giving the logo its own space.
- Black default over automatically enabling System: preserves the installed appearance;
  users explicitly opt into light/dark switching.
- A shared spec/implementation PR over a spec-only merge: the linked issue closes only
  when the complete deliverable is ready, as requested by the maintainer.

## Revision — owner feedback after first implementation

- Theme preview cards must accept mouse clicks throughout the illustrated rectangle,
  not only native radio-button glyph/title geometry. Keep radio accessibility semantics
  while using a full-rectangle push-button cell for native mouse tracking.
- Clip the square logo to 10 pt corners. Its top/bottom align with the 32 pt search
  field; its left edge aligns to the first preview image, and the search field's right
  edge aligns to the last column's preview image. Reuse the card preview inset.
- Replace the independently filled Command-F keycap with plain shortcut text blended
  into the search field. Visibility rules remain unchanged.
- Use semantic primary text for both query and placeholder: light text on dark
  backgrounds and dark text on white. Retain theme-aware text throughout the panel.
