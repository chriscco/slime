## 1. 这个 spec 要做什么

四件事，量级差得很远：

| # | 事 | 量级 |
|---|---|---|
| 1 | 卡片显示**真实窗口缩略图**（现在是 app 图标） | 大头：新增一个系统边界 + 一项 TCC 授权 |
| 2 | 面板里按 **⌘,** 直接开设置 | 小：`Trigger` 加一个事件 / 效果 |
| 3 | 玻璃**浓度**可调 + 高亮线条加粗改色 | 小：一层遮罩 + 换一处颜色来源 |
| 4 | 列表**按 app 聚拢** | 小：`sort` 加 4 行 |

第 1 件正是 0.0.2 spec §3 里那条非目标：

> \| **真截图缩略图** \| 台前调度会把搁置的窗口抓成斜的，那个 spike 还没跑 \| 0.0.2 之后，先跑 spike \|

**spike 跑完了，结论在 §4。** 按规矩追加 decision 条目，不删旧条目。

## 2. 验收标准

1. 按住 ⌘ 按 Tab 唤出面板：每张卡显示对应窗口的**真实内容**，不是 app 图标
2. 同一个 app 开两个窗口、且两个都刚用过：两张卡在网格里**相邻**
3. **冷启动后**（还没切过任何 app）唤出面板：同一个 app 的多个窗口仍然相邻
4. 台前调度搁置的窗口**不会**显示成空白或倾斜的图 —— 要么是它搁置前的样子（缓存），
   要么是 app 图标
5. 面板里按 **⌘,**：设置窗口打开，面板隐藏
6. 拖动玻璃浓度滑块 → 重新唤出面板，背后内容的可见度跟着变；**文字和图标不跟着变淡**
7. 浓度最弱时完全看不到面板后面的内容；最强时完全透明
8. 高亮线条变粗，颜色是设定值；改设置后跟着变
9. **没给屏幕录制权限时面板照常可用**，卡片显示 app 图标；不卡住、不崩溃
10. 0.0.2 的 13 条人工验收 + 0.0.1 的 10 条全部仍然通过

## 3. 非目标

| 不做 | 为什么 | 什么时候做 |
|---|---|---|
| **⌘S 切换排序** | 空 query 下列表已经是最近使用序。加个切换等于允许把它调成「不按最近使用」，那是反功能 | 有人明确要「不按最近使用」的排序时 |
| **视觉分组**（app 之间加间隔 / 标题） | 只做排序聚拢。视觉分组要重算 `GridLayout` 的格子数（它是纯函数，改动面大一个量级），而且聚拢之后卡片本来就相邻了 | 卡片相邻了还是分不清哪几扇窗属于同一个 app 时 |
| **面板背景色可调** | 这一版明确不允许改，只允许调浓度 | 想要固定色以外的底色时 |
| 鼠标点选卡片 | 0.0.1 起就是非目标 | 键盘主链路被鼠标党抱怨时 |
| 缩略图随时间自动刷新 | 只按窗口状态（枚举完成）刷新；缩略图会随时间过期，但「认出这是哪个窗口」够用 | 过期图真的误导人时 |
| 抓取其他 app 的**非窗口**内容（桌面、菜单栏） | 切换器的目标只有窗口 | 不做 |

## 4. 台前调度 spike 的结论（★ 第 1 件的前提）

### 4.1 搁置窗口没有可靠的实时抓取路径

对同一个搁置窗口，三条路各有各的坏法：

| 路径 | 搁置窗口的结果 |
|---|---|
| ScreenCaptureKit（`SCContentFilter(desktopIndependentWindow:)`） | **倾斜的透视条带**（台前调度在合成层就把窗口渲染成斜的） |
| 私有 `CGSHWCaptureWindowList(conn, &id, 1, 0)` | 不稳定：4 个搁置窗口分别给出**正的** / **全白** / **斜的**（第四个没看） |
| 私有 `CGSHWCaptureWindowList(..., 1<<19)`（"fullSize"） | **全白**。`(1<<11)\|(1<<8)\|(1<<19)` 这个组合也一样 —— 那条被广泛转述的「fullSize 能拿到未变换的窗口」实测不成立 |

**`1<<19` 只改输出缓冲区的大小，不决定源内容**：`系统设置` 的 frame 是 82×97，
裸调用给 `164×194`，加 `1<<19` 给 `1480×1250` —— 尺寸对了，内容全白。

### 4.2 私有 SkyLight 的另外那个符号也翻不动

`SLSCaptureWindowsContentsToRectWithOptions` 符号在 SkyLight 里存在，但**没有任何公开签名**
（精确短语检索零结果）。**不瞎猜签名去调私有框架** —— 参数猜错有把 WindowServer 搞崩的风险，
收益不成比例。这条路到此为止。

### 4.3 `isOnScreen` 区分不了搁置窗口

实测（同一次枚举）：

| 窗口 | frame | `isOnScreen` |
|---|---|---|
| 系统设置「外观」（搁置） | 82×97 | **1** |
| 富途牛牛（搁置） | 125×194 | 0 |
| Code（搁置） | 133×140 | 0 |
| ChatGPT（搁置） | 137×140 | 0 |
| 企业微信（**别的 Space**，正常大小） | 1085×867 | 0 |
| Chrome（别的 Space） | 1920×992 | 0 |

**搁置窗口的 `isOnScreen` 在 0 和 1 之间反复横跳**，而「别的 Space 的正常窗口」也是 0。
所以它既不能用来找搁置窗口，也不能用来判「这个窗口能不能抓」。
**「只抓在屏窗口」这条干净规则不成立。**

### 4.4 正常窗口完全没问题

在屏的 Warp / Chrome：SCK 抓到全分辨率、17–100 ms（中位约 22 ms）；私有 CGS 更快（14–20 ms）
且能抓个别 SCK 失败的 Chrome 窗口。**速度差和时间稳定性都不构成选私有 API 的理由。**

### 4.5 结论

**搁置窗口不实时抓。** 它的卡片走「缓存上一张好图 → app 图标」的逐级降级。
这不是退而求其次 —— 用户看到的会是它搁置**前**的全分辨率样子，比任何实时抓取都清楚。

图缓存按 `windowID` 存。**窗口关掉就不会再显示**：面板只渲染当前快照里的窗口，
缓存按快照边界清理，所以已关闭的窗口没有任何东西在渲染它（这是需求方明确问过的一条）。

## 5. 缩略图

### 5.1 API：ScreenCaptureKit（公开）

**不用私有 SkyLight**，尽管它快 ~10 ms 且能多抓一类 Chrome 窗口。理由：`dlopen` + 零文档 +
每次 macOS 升级赌一次，换 10 ms 和一类边缘窗口，不值。CLAUDE.md 第一条第 4 级明说优先平台原生能力。

```swift
let content = try await SCShareableContent.excludingDesktopWindows(
  false, onScreenWindowsOnly: false)
let config = SCStreamConfiguration()
config.width = …; config.height = …; config.showsCursor = false
let image = try await SCScreenshotManager.captureImage(
  contentFilter: SCContentFilter(desktopIndependentWindow: scWindow),
  configuration: config)
```

`SCScreenshotManager.captureImage` 是 completionHandler 的 ObjC 方法。**async 版本只在 async
函数体内正确解析**（spike 里在顶层代码里被推成 `Void`，编译报错）。

### 5.2 新模块：`Sources/slime/System/WindowThumbnails.swift`

**这是新的系统边界**（CLAUDE.md 第六条允许 `System/` 下新增文件的门槛），所以不是「往已有文件里塞」。
源文件 17 → 18。

职责只有两件：**缓存**（`windowID → CGImage`）和**按需抓取**。**不碰 AppKit 的视图**，
视图那边只问它要一张图。

### 5.3 抓取时机：挂在已有的枚举钩子上

`AppDelegate` 里已有「枚举完成 → `AppIcons.warm(windows)`」这个钩子，缩略图预热挂同一个地方。
这样**面板第一帧就是完整的**，不会出现「先图标、200 ms 后换成缩略图」的跳变
（0.0.2 §9 图标预热就是为了这个）。

**红线 4**：抓图同样是跨进程 IPC，**全部在后台线程**，主线程只读缓存。
**红线 5**：抓取带 generation，枚举结果过期就丢。
**红线 8**：缓存发布时整体替换，不做共享可变状态。

### 5.4 卡片的样子

缩略图是**横向**的（窗口都接近 16:10），而现在的卡片是**竖向**的（112×92，为 64pt 图标设计）。

**规格**：卡片改成横向，`cardWidth`/`cardHeight` 待定（提案 `160×120`：图区 160×100 + 间隙 + 标题 18），
`maxColumns` 可能要从 5 降到 4 —— **面板会变宽，要对着小屏验一次**。缩略图**按长宽比缩放整窗可见**
（不裁切），多出来的边用面板底色补。

抓不到缩略图时，卡片退回现在的样子（app 图标 + 窗口名），**尺寸不变** —— 混排时不该有两种卡形。

### 5.5 抓取失败的判据 —— **未决，见 §16**

## 6. 屏幕录制权限（第二项 TCC）

**这是 0.0.3 新增的、实打实的用户摩擦，要写清楚。**

- `CGPreflightScreenCaptureAccess()` 检测，`CGRequestScreenCaptureAccess()` 触发系统弹窗
- 和辅助功能**同性质**：绑代码签名（CLAUDE.md 第五条）、**授权后要重启 slime 才生效**
- 没授权时 **slime 必须照常可用** —— 面板照开、搜索照用、切换照切，只是卡片显示 app 图标。
  **这条是硬要求，不是「最好能」**：一个切换器因为缺权限就不能切窗口，等于把用户的 ⌘+Tab 弄没了
- 引导挂在现有 onboarding 的位置（`AppPermission` / `AppDelegate` 那条链路），文案要写明「要重启」

> **不检测**「用户是不是在设置里勾上了但没重启」这类中间态 —— 检测不了，只能靠文案说清。

## 7. 玻璃浓度（★ 这一节推翻 0.0.2 §7 的一个假设）

### 现状与实测

0.0.2 §7 把玻璃参数写成「`style` / `tintColor` / `cornerRadius`」三个。**`tintColor` 这条不成立。**

实测：五块 `NSGlassEffectView`（`.regular`），`tintColor = NSColor.black.withAlphaComponent(a)`，
`a` 取 `0 / 0.25 / 0.5 / 0.75 / 1.0`，放在同一张彩虹底上截图 —— **五块长得一模一样**，
彩虹照样透出来，纯黑 tint α=1.0 也没让任何一块变暗。`NSGlassEffectView` 也没有 opacity 属性。

### 方案：遮罩层

**在玻璃之上、内容之下盖一层实色遮罩**，颜色固定，alpha = `1 − 浓度`：

```swift
// PanelWindow.applyGlassSettings(_:)
content.layer?.backgroundColor = Self.panelBase
  .withAlphaComponent(1 - settings.glassStrength).cgColor
```

`PanelContentView` 本身就是玻璃的 `contentView`（已在 `wantsLayer = true`），**不用新增视图**。

实测这个方案：遮罩 α `0 → 1.0`，背后彩虹从「完全透出」到「完全消失」，
而**五块里的文字始终锐利** —— 这正是 `tintColor` 那条路给不了的（整体改 alpha 会连内容一起淡掉）。

- `panelBase` 是**固定常量**（这一版不允许改背景色）。取黑还是深灰，实现时对着玻璃看一眼定
- 设置页：**删掉「色调」色板**，那个位置放浓度滑块（0…1，默认给偏透明的值）
- `PanelWindow` 里 `glass.tintColor = …` 那行**删掉**

## 8. 高亮线条

### 加粗

`HighlightView.borderWidth` `2` → **`2.5`**。`cornerRadius` 12 不动，填充仍 `0.08` 透明度。

### 换色来源

现在是 `NSColor.selectedContentBackgroundColor`，实测三个候选（深/浅外观各取一次）：

| 候选 | 深色 | 浅色 | α |
|---|---|---|---|
| `controlAccentColor` | `(0.969, 0.510, 0.106)` 亮橙 | **完全相同** | 1.0 |
| `selectedContentBackgroundColor`（现在用的） | `(0.788, 0.376, 0.012)` 暗橙 | `(0.851, 0.420, 0.039)` | 1.0 |
| `keyboardFocusIndicatorColor` | `(1.000, 0.702, 0.227)` 偏黄 | 又不一样 | **0.5** |

**但 0.0.3 不用其中任何一个 —— 改成固定默认色 + 用户可自定义。**

理由：系统只提供 9 个值（`AppleAccentColor` = -1 多彩 + 0…7），绑上去就意味着「系统主题色一改，
slime 的高亮跟着变」，这是需求方明确不要的耦合。固定色少一个分支、少一个「跟随系统」勾选框。

**默认值提案 `(0.969, 0.510, 0.106)`** —— 不是因为它好看，是因为它**实测过**：
上面那张截图里，这个橙在近黑的面板底上、2.5pt 线条下对比度够。换别的颜色要重测一轮。

**存储**：`Settings.glassTint: NSColor?` → 改名成 `Settings.highlightColor: NSColor`（不再是可选）。
设置页那个 `tintWell` **不删、改名留用**（`highlightWell`），只是换了控制对象 ——
这样净变更更小（item 3 本来要「删掉色调色板」，现在等于把它挪了个用途）。

**传递**：`HighlightView` 拿不到 `Settings`。面板 `show()` 时本来就读一次设置，
顺手把颜色推给 `CardGridView` 即可（不做观察者，理由同 0.0.2 §8）。

## 10. 按 app 聚拢（★ 这一节修一个现存 bug）

### 现在为什么不聚拢

```swift
let ra = rank[a.element.pid] ?? Int.max     // ← 没进过 MRU 的 app 全拿 Int.max
let rb = rank[b.element.pid] ?? Int.max
return ra != rb ? ra < rb : a.offset < b.offset
```

名次并列就退回窗口列表的 **z 序** —— 而 `mruPids` **启动时是空的**，只在你切过 app 之后才填。
所以冷启动后大多数 app 名次并列，它们的窗口按前后顺序**交错**在一起。
（现象：用过的 app 浮到前面聚成一坨，没用过的一堆挤在后面乱着。）

### 修法：给没名次的 app 也发不重复的名次

```swift
var next = mru.count
for window in windows where rank[window.pid] == nil {
  rank[window.pid] = next
  next += 1
}
```

按 **app 在窗口列表里第一次出现的位置**编号。加这 4 行：同一个 app 的窗口必然相邻；
app 之间仍按 MRU（用过的在前），没用过的按 z 序排在后面。**不动 `GridLayout`，不动视图。**

### 可测性

`sort` 现在是 `private nonisolated static`。**放开到 `internal`**，用 `@testable import` 直接测 ——
4 行的改动不值得为它搬到 `Core/`（CLAUDE.md 第六条「加文件之前先问能不能并进已有的那个」）。
**这是对「只有 Core 能单测」的一处有意偏离，记进 `decision.md`。**

## 12. 人工验收清单

- [ ] 唤出面板：每张卡是**窗口真实内容**，不是图标
- [ ] 同一个 app 两个窗口 → 两张卡相邻
- [ ] **冷启动后**（还没切过 app）唤出面板 → 同一个 app 的窗口仍然相邻
- [ ] 台前调度搁置的窗口：不出现空白 / 倾斜的图；显示的是缓存图或图标
- [ ] 关掉一个窗口再唤出面板：它的卡片**不在了**（缓存没有被渲染出来）
- [ ] 面板里按 ⌘, → 设置窗口在前，面板收起
- [ ] 拖浓度滑块 → 重新唤出面板：背后可见度跟着变，**文字 / 图标没有变淡**
- [ ] 浓度最弱 → 完全看不到背后；最强 → 完全透明
- [ ] 高亮线条明显变粗；改高亮色后跟着变
- [ ] **在系统设置里取消勾选屏幕录制 → 重启 slime → 面板照常可用**，卡片退回图标
- [ ] 卡片变大后面板仍然放得下（小屏 / 窗口多时）
- [ ] 0.0.2 的 13 条 + 0.0.1 的 10 条全部仍然通过

## 13. 已知风险与待验证

| 风险 | 怎么验 | 什么时候 |
|---|---|---|
| 抓图把「按下即出面板」拖慢（0.0.1 §7 的承诺） | 确认抓取**完全**在后台，主线程只读缓存；量一次首次唤出的延迟 | 写完缩略图那步 |
| `SCWindow` 对象会过期，每批抓取可能要重取 `SCShareableContent`（本身不便宜） | 量一次批量抓取的总耗时 | 同上 |
| SCK 在部分 Chrome 窗口上失败（历史见过 `-3811`） | 真机跑一遍 Chrome | 同上 |
| 卡片改成横向后面板变宽，小屏放不下 | 对着最窄的屏幕验 | 改 `GridLayout` 常量时 |
| 浓度最强时是否**真的**完全透明（玻璃材质本身仍在折射） | 真机对着桌面看 | 写完遮罩那步 |
| 屏幕录制权限被中途撤销（用户在设置里取消勾选） | 走 §12 那条取消勾选的验收 | 全程 |

## 14. 代码里要留的 `shortcut:` 注释

```swift
// shortcut: 缩略图缓存只按 windowID 存，不做时间戳 / TTL —— 窗口关了就在快照边界清掉；
//           真的出现过期图误导人时再加时效
// shortcut: 抓图走 SCK 公开 API，没用私有 SkyLight 的 CGSHWCaptureWindowList
//           （它快 ~10ms 且能多抓一类 Chrome 窗口）—— 慢到感觉得出来时再说
// shortcut: 玻璃浓度是一层遮罩，不是玻璃本身的属性（NSGlassEffectView 没有 opacity，
//           tintColor 的 alpha 实测无效）—— Apple 给出真属性时换掉
// shortcut: 排序聚拢只保证同一 app 的窗口相邻，不做视觉分组（app 之间加标题）——
//           相邻了还是分不清哪几扇窗属于同一个 app 时再做
```

## 16. 未决问题

- **抓取失败的判据怎么定？** §4.3 已实测 `isOnScreen` 不可用。三条路：
  (a) 全抓 + 丢弃「空白」结果（要写一个粗采样判空的函数）；
  (b) 按 frame 大小设门槛（小于某尺寸不抓，退回缓存 / 图标）；
  (c) 全盘接受（会显示空白或倾斜的图，最丑但代码最少）。
  **倾向 (a)** —— 空白才是最丑的那种，(b) 用的正是红线 7 警告过的「按尺寸判断」。
- **卡片尺寸 / 长宽比**：§5.4 的 `160×120`、`maxColumns` 5→4 都只是提案，要对着真机调。
- **卡片上要不要留一个小 app 图标角标**：缩略图本身认不出是哪个 app（尤其两个 app 长得像时）。
- **屏幕录制权限什么时候要**：启动时跟辅助功能一起（本文案倾向），还是设置页里显式开启？
  启动时多一个系统弹窗，但缩略图是这一版的主交付物；显式开启则默认没有缩略图。
- **缩略图刷新时机**：只挂「枚举完成」，还是面板 `show()` 时对当前快照补抓一次？
- **`WindowCache.sort` 放哪**：留在 `System/` 放开 `private`（本文倾向），还是提到 `Core/`
  以符合「纯逻辑进 Core」？后者要新增文件，和「源文件保持精简」冲突。
