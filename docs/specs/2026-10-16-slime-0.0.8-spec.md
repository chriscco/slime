## A. README media and installation

Keep the existing banner. Place a compact demonstration section after the introduction,
before installation: one short switching/search GIF and up to two static screenshots
(panel themes and settings). Use real captures, readable at README width, with no private
window titles, account information, or notifications. Both READMEs reuse the same assets
under `docs/assets/` with localized captions and meaningful alternative text. Static
images must still explain the feature without watching the animation. Aim for a GIF
under 5 MB and screenshots under 1 MB each; optimize or shorten before adding large files.

Final assets are supplied or approved by the user. Do not invent screenshots or commit
broken image placeholders while waiting for assets.

Remove the mandatory checksum download and terminal command from both README installation
flows. The normal steps are download DMG, drag to Applications, handle the existing macOS
opening prompt if needed, grant Accessibility, and restart. Keep optional Screen Recording
and source-build guidance concise. Continue publishing SHA-256 files and verifying them
in release CI; this is a documentation simplification, not removal of artifact validation.
Do not add development-version/latest-DMG notices to either README.

Acceptance: both language guides agree; links and assets render on GitHub; a DMG user
can follow installation without Terminal; no private information appears in the media.

## B. Preview source preference

### Evidence and choices

`WindowThumbnails` already uses ScreenCaptureKit single-window screenshots, memory and
disk caches, and negative caching for unavailable windows. `looksLikeWindowRender` rejects
images with transparent corners, including some perspective-shaped Stage Manager renders.
Other captures fail outright or return blank images. Disabling caching alone cannot make
an unavailable window capturable.

Recommended UI: an Appearance preference named **Preview source**, with **Cached previews
(recommended)** and **Fresh captures**. This is clearer than promising live video or complete
Stage Manager access. Default to cached previews, preserving existing behavior. A simpler
alternative is to allow perspective renders only when no good cache exists; that improves
fallbacks but does not fulfill a user's choice to avoid stored previews.

### Proposed fresh-capture contract

- Start a new capture batch when opening the panel or explicitly refreshing the window
  snapshot. Capture once per window per batch; no continuous stream or per-keystroke capture.
- Do not read or write persistent thumbnail files, or reuse images from previous panel
  sessions. Temporary images and request deduplication within the current session remain
  necessary; "fresh" does not mean retaining zero image data in memory.
- Accept nonempty perspective-shaped images; fit them proportionally in the existing card
  canvas without stretching or pretending to reconstruct the original rectangle. Keep
  transparent margins. Reject wholly transparent/blank results and retain the fallback.
- A failed window gets at most one attempt per panel session unless it becomes visible;
  reopening allows another attempt. No retry loop for unavailable windows.
- Mode changes invalidate in-flight results and session images. Late old-mode captures must
  neither repaint the panel nor schedule cache writes after the change. Queued file work
  is cancelled; an already-started file operation may finish without blocking the main
  thread. Existing disk files are
  left dormant while fresh mode is active; this preference is not a secure-delete control.
- Use the existing bounded panel presentation deadline (currently 300 ms), capture off
  the main thread, and update cards when the serial capture batch returns. Do not extend the deadline or
  block switching, search, or close operations while waiting for images.
- Never activate a target app, switch Spaces, or use private capture APIs to obtain a preview.
  Without Screen Recording permission, retain the same usable placeholder behavior.

Before implementation, perform a bounded native experiment capturing a visible window,
a Stage Manager side-strip window, an unavailable other-Space window, and a minimized
window. Record which yield usable perspective images; public API availability does not
promise the same output for all states. If no useful perspective capture is reproducible,
report that result and revise the design before shipping a misleading preference.

Acceptance/tests: verify cached mode remains unchanged; fresh mode ignores disk and old
session images; mode toggles reject stale completions; failed capture does not remove the
window; perspective fixtures render while blank fixtures fall back. Exercise both modes
on Stage Manager and multiple displays. Compare 10/50/100-window planning and capture
counts; repeated search/selection must not increase capture requests. Measure native
panel responsiveness separately from synthetic CPU benchmarks.

## C. Settings window and About

### Window behavior

The controller currently creates a closable NSWindow, but no standard Close menu action
or settings-specific Command-W handling is present. Route Command-W through the AppKit
responder chain (or a settings-window-local equivalent) to `performClose:`. Verify the
event tap does not swallow it. Do not register a global close shortcut.

Acceptance: after Command-comma, Command-W closes only settings, from every sidebar
section and with a focused control. slime and other applications stay running. Settings
can reopen, preferences persist, and a foreground window in another app retains its
normal Command-W behavior.

### About layout

Reuse `docs/assets/slime-banner.png` (2172 × 724, 3:1) as a bundled, local resource.
At the current 720-point settings width, the content column is approximately 490 points:
show a full-width, roughly 163-point-high banner with 12-point rounded corners and no
shadow or extra border. Preserve the artwork without cropping. Below it, align version,
GitHub link, and update controls to the same leading edge with 16–24-point spacing.
The artwork already carries the slime name; avoid repeating an oversized title. Provide
an accessibility label for the banner. Use semantic text colors in light and dark modes.

Build scripts must copy the resource into the app; loading must not depend on a repository
checkout or working directory. Check the packaged app, not only `swift run`. Missing
artwork falls back to the text name without breaking About or creating a layout gap.

## Update delivery: Sparkle confirmed

On 2026-10-16, the user selected in-app downloading, installation after confirmation,
and relaunch. Use Sparkle 2 for checking, downloading, validation, replacement, and
relaunch. This is the project's first third-party runtime dependency, justified by
avoiding a custom executable installer.

A check-only feature that opens a release page was considered and not selected.
A manual download link may remain as a recovery option, but does not satisfy this scope.

Writing a bespoke self-replacing installer is not proposed: safe replacement, interrupted
updates, permissions, validation, and restart behavior are already handled by Sparkle.

### Sparkle design

The app fetches an HTTPS appcast containing version, compatibility, download URL, and
archive signature. A bundled public Ed25519 key verifies archives signed by a separate
private update key. These keys are separate from the existing code-signing certificate;
a checksum alone is not update authentication. The private key belongs in protected
release secrets and a secure backup, never in the repository or PR logs.

Provide a "Check for Updates…" button and an opt-in automatic-check preference. Use
Sparkle's standard update dialog, showing release information and allowing install/later.
No silent installation or forced restart in this version. Background checks use the
framework's schedule rather than a new timer, never the window enumeration loop.

Pin a supported stable Sparkle version. Integrate its framework/helper packaging into
SwiftPM and the manual bundle script, preserving framework symlinks, executable modes,
runpaths, and correct nested signing. First prove operation with the project's existing
self-signed, unnotarized distribution on macOS 26; do not claim EdDSA makes it notarized
or removes Gatekeeper prompts. Preserve app bundle identity and signing continuity.

Extend the tagged-release workflow to generate signed update metadata for the verified
artifact and reviewed English release notes. Serve an appcast at a stable HTTPS location
(proposed: a release asset reachable through GitHub's latest-release download endpoint).
Validate redirects and failure behavior before adopting that endpoint. Publish artifacts
and metadata together only after tests, version matching, and signature checks pass;
failed publication must leave the previous usable update feed intact. No beta channel,
delta updates, analytics, or separate update server is required for this version.

Acceptance: using isolated old/new builds and a test feed, verify successful install and
relaunch, opt-out, cancellation, offline handling, corrupted archive/bad-signature refusal,
unsupported OS/architecture filtering, no downgrade/reinstall for equal versions, and
failure while running from a read-only DMG. Failed checks or downloads preserve the current
working installation and do not interfere with the panel. Check Accessibility and Screen
Recording behavior after a real signed upgrade rather than assuming permissions persist.

Existing 0.0.7 builds have no updater: users must install the first updater-enabled version
manually. Only subsequent upgrades can use the new update path. Keep ordinary DMGs available.

### Acceptance follow-up: Accessibility onboarding

When enabling slime without Accessibility access, request the macOS permission
prompt only. The user chooses Deny or Open System Settings in the system dialog.
Do not show an additional slime-owned denial alert or open System Settings
automatically. macOS controls whether repeated requests display its prompt. Before either system permission request, hide Settings so a floating window cannot
cover the system dialog even when macOS does not send a resign-key notification.
Users can reopen Settings from the menu bar afterward.

Fresh installations default to enabled and start permission onboarding at launch.
Missing Accessibility access prevents keyboard interception but must not persist
`enabled = false`: after granting access, restarting resumes normal startup without
requiring a visit to Settings. Preserve an explicit user opt-out across launches.

The Enable slime switch reflects actual keyboard handling, not just the saved
startup preference. After denied authorization it displays off, while preserving
startup intent. Turning it on retries authorization. Unrelated settings changes
must not retry enabling or request permission.

The same-window native comparison is in progress; this amendment does not itself
